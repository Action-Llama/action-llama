title: "Gateway API"
description: "HTTP API for controlling the scheduler, triggering agent runs, and streaming status"

The gateway is the HTTP server that runs alongside the scheduler. It handles webhooks, serves the [web dashboard](/reference/web-dashboard), and exposes control and status APIs used by CLI commands and the dashboard.

The gateway starts automatically when needed — either when webhooks are configured, when `--web-ui` is passed to `al start`, or when Docker container communication is required. The port is controlled by the `[gateway].port` setting in `config.toml` (default: `8080`).

## Authentication

The gateway API is protected by an API key. The same key is used for both browser sessions and CLI access.

**Key location:** `~/.action-llama/credentials/gateway_api_key/default/key`

The key is generated automatically by `al doctor` or on first `al start`. To view or regenerate it, run `al doctor`.

### CLI access

CLI commands (`al stat`, `al pause`, `al resume`, `al kill`) automatically read the API key from the credential store and send it as a `Bearer` token in the `Authorization` header.

### Browser access

The [web dashboard](/reference/web-dashboard) uses cookie-based authentication. After logging in with the API key, an `al_session` cookie is set (HttpOnly, SameSite=Strict) so all subsequent requests — including SSE streams — are authenticated automatically.

### Protected routes

The following routes require authentication:

- `/dashboard` and `/dashboard/*` — all dashboard pages and SSE streams
- `/control/*` — scheduler and agent control endpoints
- `/sessions/*` — session listing and WebSocket attach
- `/locks/status` — active lock information

Health checks (`/health`), webhook endpoints (`/webhooks/*`), and container management routes are **not** protected.

### Migrating from `AL_DASHBOARD_SECRET`

The old `AL_DASHBOARD_SECRET` environment variable (HTTP Basic Auth) is no longer used. If it's still set, a deprecation warning is logged. Remove it from your environment and run `al doctor` to set up the new API key.

## Control API

All control endpoints use `POST` and require authentication.

### Scheduler control

| Endpoint | Description |
|----------|-------------|
| `POST /control/pause` | Pause the scheduler (all cron jobs) |
| `POST /control/resume` | Resume the scheduler |

### Agent control

| Endpoint | Description |
|----------|-------------|
| `POST /control/trigger/<name>` | Trigger an immediate agent run |
| `POST /control/agents/<name>/enable` | Enable a disabled agent |
| `POST /control/agents/<name>/disable` | Disable an agent (pauses its cron job) |
| `POST /control/agents/<name>/pause` | Pause an agent (alias for disable) |
| `POST /control/agents/<name>/resume` | Resume an agent (alias for enable) |
| `POST /control/agents/<name>/kill` | Kill all running instances of an agent |

## Session API

The session API exposes active agent sessions and a WebSocket endpoint for attaching to a running session in real time.

### REST endpoints

| Endpoint | Description |
|----------|-------------|
| `GET /sessions` | List all active sessions (status `running` or `waiting`). Returns `{ sessions: AgentSession[] }`. |
| `GET /sessions/:id` | Fetch a single session by ID. Returns `{ session: AgentSession }` or `404`. |

**`AgentSession` fields:**

| Field | Type | Description |
|-------|------|-------------|
| `id` | string | Unique session identifier |
| `agentName` | string | Name of the agent |
| `status` | `running` \| `waiting` | Current lifecycle state |
| `startedAt` | string (ISO 8601) | When the session started |
| `trigger` | string | What triggered this session (e.g. `schedule`, `webhook:github`, `manual`) |

### WebSocket attach

Upgrade a connection to `GET /sessions/:id/attach` to attach to a running session. The server streams JSONL events over the WebSocket and accepts command messages from the client.

**Upgrading:**

```bash
# Using websocat (example)
websocat -H "Authorization: Bearer <key>" \
  ws://localhost:8080/sessions/dev-3a1b2c4d/attach
```

Authentication uses the same `Authorization: Bearer <key>` header as the HTTP API. Connections without a valid key are rejected with `401`.

**On connect**, send a `get_state` command to receive the full session transcript:

```json
{"type":"get_state"}
```

The server responds with a `state_snapshot` event containing the current Pi session state (messages, model, status).

**Client → server commands (JSONL):**

| Command | Description |
|---------|-------------|
| `{"type":"get_state"}` | Request the current session state snapshot |
| `{"type":"steer","message":"..."}` | Inject a steer message into the agent's current turn |
| `{"type":"abort"}` | Cancel the current turn and end the session |

**Server → client events (JSONL):**

The server forwards all Pi session events as JSONL, one event per line. Key event types:

| Event type | Description |
|------------|-------------|
| `state_snapshot` | Full session state (sent in response to `get_state`) |
| `message_update` | Streaming token-by-token assistant output |
| `turn_end` | A turn completed |
| `tool_execution_start` | Tool call started |
| `tool_execution_end` | Tool call completed (includes `isError`) |
| `agent_end` | Session reached terminal state — connection closes after this |
| `error` | An error occurred in the session |

**Disconnect behaviour:**

- When the session completes normally, the server sends a final `agent_end` event and closes the connection.
- If the session is in a `waiting` state, the WebSocket stays open and sends a state update. The client remains attached.
- Detaching (closing the client socket) does not affect the running session.
- Multiple clients can attach to the same session simultaneously; all receive the same event stream.

<Info>The Pi extension (`pi -e @action-llama/action-llama/extension`) uses this protocol to power the `/sessions` and `/attach` commands. See the [Pi integration](/integrations/pi) for the user-facing interface.</Info>

## Status API

### SSE streams

Live updates use **Server-Sent Events (SSE)**:

| Endpoint | Description |
|----------|-------------|
| `GET /dashboard/api/status-stream` | Pushes agent status and scheduler info whenever state changes |
| `GET /dashboard/api/logs/<agent>/stream` | Streams log lines for a specific agent (500ms poll interval) |

### Trigger history

| Endpoint | Description |
|----------|-------------|
| `GET /api/stats/triggers` | Paginated trigger history (cron, webhook, agent-call). Supports query params: `page`, `limit`, `deadLetter` (boolean). |
| `POST /api/webhooks/:receiptId/replay` | Re-dispatch a stored webhook payload by receipt ID. Returns the dispatch result. |

### Health check

| Endpoint | Description |
|----------|-------------|
| `GET /health` | Health check (no authentication required) |

### Lock status

| Endpoint | Description |
|----------|-------------|
| `GET /locks/status` | Active resource lock information (requires authentication) |
